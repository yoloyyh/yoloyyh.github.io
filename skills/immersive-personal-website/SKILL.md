# 沉浸式个人网站

把个人站视为可使用、可维护的作品，而不仅是一张概念图。围绕真实经历和可验证内容构建场景；让访客能轻松找到项目、文章和联系方式。

## 1. 理解用户与内容

- 确认网站用途、目标读者、个人身份、设备和部署方式；参考已有对话与工作区，避免重复询问已经回答的问题。
- 区分原创项目、确有本人贡献的开源项目和仅供参考的收藏。不得把 Fork 自动当作贡献，也不得编造工作职责、成果或量化指标。
- 了解项目和文章的真实数量，再选适合扩展的列表、分类、搜索和详情布局；多项目不应都塞进一个弹窗。
- 对知识库默认私有；只有明确标记允许公开的文章才进入公开数据。说明本地预览、公开导出和线上部署之间的区别。

## 2. 设计可理解的世界

- 基于用户喜欢的文化元素、职业特点和参考网站，提出可实现的视觉方向；避免照搬受保护的旋律、商标或角色形象。素材、音乐和音效在公开使用前核对来源与许可。
- 优先设计一个真实入口与主要路径：首屏 → 场景内 → 项目/文章 → 返回。每个标题、标签和按钮都要有用途，删除无意义的装饰文案。
- 让场景叙事、视觉和功能对应：例如书架上的项目入口应锚定书架；大门、光点和过场终点应共享同一位置；人物应真正进入入口，而非在画面中随机飞行。
- 场景素材应融合透视、光线、比例和遮挡。生成建筑、楼梯、门等结构后仔细检查连续性、支撑、扶手和上下层连接；发现结构错误应重新设计或重绘，而非反复移动一层装饰图。
- 将可复用的视觉层与交互层分开；使用同一图像坐标系定位热点、物体路径和终点，并考虑背景 `cover` 裁切、视差、滚动及容器尺寸变化。

## 3. 实现和迭代

- 优先使用仓库现有技术与设计语言；保证静态部署可行。按需制作本地素材，控制尺寸和格式；背景优先加载，热点在背景准备好后才出现。
- 动效要表达因果与方向：门先打开，角色再进入；列车沿桥面行驶并从桥头出现；飞行动物朝移动方向飞行，离屏后再循环。避免干扰阅读或遮挡交互。
- 声音默认可控制，考虑浏览器自动播放限制。音效与用户动作对应，降低音量，避免循环突兀；素材需可离线加载且使用权清晰。
- 图片导出前检查透明边缘和多余光晕。纸张、羽毛、云雾等自然元素应有可信的材质和运动，不把模糊圆点直接当成真实物体。
- 文章渲染应支持常用 Markdown、代码块、表格和安全链接；Obsidian 内部链接不得意外暴露私有笔记。优先修复网站的统一渲染而不是改写所有笔记。
- 国际化需要覆盖动态内容、按钮和无障碍标签。支持键盘、焦点返回、减少动态效果和手机触控；动画完成、取消、快速重复点击都必须可恢复。

## 4. 验证真实体验

按 [references/qa-playbook.md](references/qa-playbook.md) 检查桌面、手机、重复进出、慢加载、音效、语言切换和公开数据。测试核心状态与数据边界；视觉问题要检查实际画面，无法观察时明确告知，不把单元测试当成视觉验收。

## 5. 部署与交付

- 公布前列出将上传的文件和文章；排除私有预览、未授权音乐、令牌和无关目录。验证部署产物，而不只依赖 `.gitignore`。
- GitHub Pages 的自动化可以刷新公开 GitHub 仓库，但本地 Obsidian 数据不会自动出现在云端；明确同步、提交、部署以及撤回的边界。
- 用户授权发布后检查仓库、工作流、发布状态和实际站点。若权限、自动审批或登录阻止，保留已完成的本地成果，准确说明阻塞位置，不绕过限制。
- 交付时说清修改、验证、当前是否上线，以及需要用户体验确认的部分；根据具体反馈继续调整，不虚构成功结果。
